- 日期：2026-08-01
- 项目路径：`~/agent-learning/danchi-monitor/`
- 状态：设计已与用户确认，待实现

## 1. 背景与目标

用户在 9 月要搬到新的 UR 团地，想监控东京圈（东京 / 千叶 / 埼玉 / 神奈川）UR賃貸住宅是否有新的、符合条件的可租空房。这是一个真实需求 + 学习项目（学 agent / 自动化 / 数据 pipeline）。

**核心诉求：** 一旦出现符合条件的新空房，尽快通知用户（Discord），并提供打分帮助决策。

**基准：** 要优于"金町 · 步行2分 · 43㎡ · 9.5万/月 · 1DK和室"这个已推荐房源。

---

## 2. 用户需求（精确条件）

| 维度 | 硬条件（不满足则淘汰） | 偏好（影响打分） |
|---|---|---|
| 通勤 | 电车到**浜松町 ≤60分** | 越短越好 |
| 步行 | 到最近车站 **≤10分**（其他条件好可放宽到15分） | 越近越好 |
| 月租 | **≤10万日元** | 越便宜越好 |
| 面积 | **≥40㎡** | 越大越好 |
| 楼层 | **3层以上必须有电梯** | 低楼层更好（非必须） |
| 户型 | — | **洋室 > 和室**（非必须） |
| 翻新 | **必须翻新过，不能太旧** | — |
| 地域 | 东京/千叶/埼玉/神奈川 | **东京优先** |

## 3. 数据源（已实测验证）

### 3.1 UR 官网 JSON API（主数据源）

- **API base**：`https://chintai.r6.ur-net.go.jp/chintai/api/`
- **站名联想**：`station/suggest/`（POST，`search_value` + `block`）→ 已验证，浜松町 station_cd = `2827`
- **团地列表（搜索）**：`bukken/search/<mode>_main/` 与 `bukken/search/list_bukken/`，`mode=leadtime` 走通勤时间搜索；提交参数含 `station_cd1/cost1/change1` 等
- **房间列表**：`room/list/`（`mode=init&id=<bukkenId>`）→ 返回某个团地的具体空房
- **返回粒度**：搜索返回的是**团地级**（含空室数量），**房间级**需要再调 `room/list/` 下钻

### 3.2 通勤时间表（静态，用于发现阶段）

- 每个车站有一份 XML：`https://www.ur-net.go.jp/chintai/common/xml/cost-time/cost-time_<stationCd8位>.xml`
- 浜松町（`00002827`）的 XML 已验证可下载（185KB），内含"浜松町→各站 的 costTime / changeTimes"，即**到浜松町60分内的车站全集**
- **策略**：发现阶段下载一份浜松町通勤表，用它筛出"最寄駅到浜松町≤60分"的团地。静态文件，低频获取，不需要每次请求线路引擎

### 3.3 robots.txt（已核查）

- `robots.txt` 禁止的是 `/chintai/*/result/?skcs= / ?line= / ?station= / ?station_nm=` 这几个带特定参数的搜索结果页
- 我们使用的 API 域名（`chintai.r6.ur-net.go.jp`）与 XML 路径**不在禁用列表内**
- 但遵循"礼貌爬取"原则：低频、限速、退避

## 4. 架构总览（三层 + 两段推送）

### 4.1 三个运行阶段

```
阶段1 · 发现（每月1次）
  全东京圈团地 → 通勤表筛 ≤60分 → 目标团地列表（SQLite）
阶段2 · 单查询轮询（高频，如每5分钟）
  跑一次UR搜索（浜松町≤60 + 宽条件）→ 当前有空房的合格团地
阶段3 · 房间轮询（随阶段2触发）
  对"有空房的团地"逐一下钻 room/list → 拿到具体空房
```

### 4.2 两段式推送（异步）

```
新空房出现
  → ① 规则引擎算基础分，够格立即推Discord（快，抢时间）
  → ② 异步调LLM细评（对照条件写点评）
  → ③ LLM结果推第二波，补充"为什么值得看"
```

### 4.3 宽筛 vs 精确筛

- **UR搜索做宽筛**（放松条件，避免漏房）：月租≤11万、步行≤15分、面积≥35㎡、空室あり
- **本地规则引擎做精确筛 + 打分**：全部硬条件（月租≤10万、≥40㎡、步行≤10/15、电梯、翻新、和/洋室）
- 好处：UR搜索逻辑变动不丢房；精确判定完全本地可控；可调

## 5. 数据模型（SQLite：`data.db`）

| 表 | 用途 | 关键字段 |
|---|---|---|
| `target_danchi` | 目标团地列表（阶段1产物） | danchi_id, name, url, station_cd, station_name, walk_min, commute_min, prefecture, region, 是否active |
| `seen_rooms` | 已见过的房间（增量diff用） | room_id(主键), danchi_id, first_seen, last_seen, last_status |
| `poll_log` | 每次轮询快照（时间序列分析） | id, polled_at, danchi_id, vacancy_count, room_ids(JSON), 是否变更 |
| `history` | 评分历史 | room_id, danchi_id, found_at, score, detail(JSON), llm_comment |

**poll_log 的价值**：用户要求"记录每次轮询到的空房信息"，以便统计**哪个团地、哪个时间段会被更新** → 支持时间序列分析。

## 6. 打分系统

### 6.1 硬条件（淘汰制，全过才进打分）

1. 通勤到浜松町 ≤60分
2. 步行 ≤10分（其他条件好放宽到15分）
3. 月租 ≤10万
4. 面积 ≥40㎡
5. 3层以上必须有电梯
6. 必须翻新过（不能太旧）

### 6.2 加权打分（0-100，权重可配）

| 维度 | 初始权重 | 计分思路 |
|---|---|---|
| 通勤时间 | 30 | 60分→0，越短越高 |
| 步行 | 20 | ≤10分满分，15分递减 |
| 月租 | 20 | 10万→0，越便宜越高 |
| 面积 | 15 | 40㎡→0，越大越高 |
| 洋室>和室 | 5 | 洋室满分，和室减分 |
| 低楼层 | 5 | 1-2层满分，楼层高递减 |
| 东京优先 | 5 | 东京满分，其他递减 |

**推送阈值**：算出"基准房（金町）"的分数作为及格线，只推超过它的（可在 config 调整）。

---

## 7. 通知流程

- **渠道**：Discord（用户已配置好）
- **第一波（即时）**：新空房通过硬条件 + 分数 > 阈值 → 立即推送，含分数、关键字段、详情页链接
- **第二波（LLM点评，异步）**：后台调 LLM 生成"为什么值得看"的短评 → 补充推送
- **失败处理**：Discord 推送失败需重试；LLM 失败不影响第一波

---

## 8. 轮询频率与反封策略

### 8.1 频率（config.yaml 可调）

- **日间**（工作日 8:00-22:00）：每 5 分钟
- **夜间**（22:00-8:00）：每 30 分钟（新房概率低，减少风险）
- 每 5 分钟 = 1次搜索 + 若干次房间下钻，负载低

### 8.2 反封策略

1. 用**轻量JSON API**，不抓整页HTML
2. 固定 User-Agent + 随机抖动（避免机械节律）
3. 遇到 403/429 → **指数退避**重试，连续失败报警
4. 遵守 robots.txt（不使用被禁的 result 页参数）
5. 日志记录请求频率，方便审计

## 11. 测试计划

1. **单元测试**：`score.py`（硬条件/打分/阈值）、diff 逻辑 —— 纯函数，优先测
2. **集成测试**：跑一次 `discover`，验证目标列表正确；跑一次 `monitor`，验证能拉到空房
3. **真实数据核对**：用已知房源（金町基准房）验证打分合理性
4. **Discord 推送测试**：手动触发一次推送，确认 webhook 正常
